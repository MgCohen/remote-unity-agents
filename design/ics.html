Anchors an agent can't drift away from.Intent · Constraints · Success.

A one-page artifact, authored before planning, that fixes what a stream of work is for, where it may not go, and how you'll know it worked — then holds still while the agent builds inside it.

I
Intent
The durable why and what — plus the North Star that means this work succeeded.
C
Constraints
Guardrails. The lines the agent must not cross — written as prohibitions, not procedure.
S
Success
Observable, checkable outcomes. The bar every phase review is judged against.
01

ICS is the rung you freeze

Intent → spec → tests → code is one ladder. The only real question is which rungs a human authors and holds fixed, and which the agent regenerates. ICS is the durable top rung. The plan and specs below it are cheap to regenerate against it — so you stay spec-anchored, never spec-as-source: humans own the anchor and read the diffs.

Below the anchor the plan runs in phases, each reviewed before it lands. A feature-sized stream of work is a Box; its anchor lives in the Box's .box/ folder. Those are the units the rest of this doc steers.

Fig. 1 — the ladder: one rung is held, the rest regenerate
02

Why freeze it

Freezing may not beat merely having an anchor on any single task — a large study found random rules scored the same as curated ones. But per-task quality is the wrong axis. Freezing buys anchor integrity over the life of the work. You steer by it, so it has to stay clear and true.

The failure it prevents is specific. Let the artifact mutate freely and shipped drift leaks back into it — now you steer by a corrupted anchor while still trusting it. A present-but-wrong anchor is worse than none, because it launders bad direction as authority.

Fig. 2 — the same drift, two anchors

Drift must never flow uphill into the anchor; only a human-approved change moves it (§03).

The decision Soft-lock, not immutability. The agent never edits the ICS as a side effect of shipping. Every change is a deliberate, human-approved decision. The default is work within the anchor, not amend it. This reuses the repo's existing protected-paths + required-review governance rather than adding a new mechanism.
03

How the anchor moves

Sometimes the work genuinely proves the anchor wrong — the upstream pivot. That's allowed. What's not allowed is a quiet edit. An amendment is proposed as a change to the anchor and gated behind a high-stakes confirmation (a critical-confirm). The agent can propose, but never approve its own change; you approve it, from outside the build.

Fig. 3 — amendment is a gate, not a keystroke
04

ICS nests by altitude

One anchor rarely fits a whole system. ICS composes at three altitudes — the project constitution, a feature stream, and the implementation of one part. Each is a real ICS; what changes with altitude is scope, blast radius, and how hard it is to move. In this repo the project anchor already exists — the behavioral oracle, the top-tier spec of required behavior.

Fig. 4 — the strata: inherit downward, gate upward

Three rules make the nesting coherent:

  • Constraints inherit and tighten downward. A child may add or tighten a parent's constraints, never loosen them. Its allowed space is a subset of the parent's.
  • Success ladders upward. Every child success criterion serves a parent one; clearing all the children should roll up to clearing the parent.
  • Gating cost rises with altitude. Amending an implementation ICS is a light approval; amending the project constitution is the heaviest gate, because it invalidates the most work. Drift is cheapest to correct at the leaf and most dangerous when it reaches the top.

05

Principles

P1

Lead constraints with the negatives

In a 5,000-run study, every beneficial rule was a prohibition (“do not X”) and every harmful one a directive (“do X”). Constraints are boundaries; procedure belongs in the plan.

→ Guardrails Beat Guidance
P2

One page, on purpose

Specification cost is U-shaped: too little defers and fragments it downstream; too much rebuilds the brittleness of rigid specs. The optimum is a checkable middle. If it's becoming a PRD, you're on the wrong rung.

→ Eisele · the U-curve
P3

Soft-lock the anchor

No auto-mutation — every change is a gated decision. You're protecting the anchor's integrity, not any one task's output.

→ freeze & drift, §02
P4

Success is the review bar

Phrase it as observable outcomes with stable IDs (SC-1, SC-2) so phase reviews, tests, and PRs cite the exact criterion. Not “works well.”

→ NL-fixture boundary conditions
P5

Trace to evidence

Where a constraint or criterion has a durable source — an oracle item, an ADR, an observed friction — cite it. A constraint that traces back to nothing is just opinion.

→ IntentSpec · ProductSpec
P6

Force the non-functional guardrails

Real agent context files carry security and performance only ~15% of the time. The Constraints surface forces exactly the budgets everyone else forgets.

→ Agent READMEs corpus
06

Running against the anchor

For the life of the work, the anchor steers the plan and sets the bar for ground-up review — each phase re-checked from the bottom up against its constraints and success. A guided, bounded Q&A produces the anchor at creation; from then on the agent works against it and only the owner can move it.

Examples

A filled feature ICS

The .box/ anchor for a Box that builds the guided authoring flow itself.

  • Intent — Box creation needs defining docs, but there's no guided way to produce them; hand-authoring is skipped or inconsistent. Build a bounded Q&A that turns finite prompts into a valid ICS. North Star: creating a Box always yields a clear one-page anchor with no authoring discipline required.
  • Constraints — Must not open-endedly converse — this is the bounded sibling of planning. Must not add a second flow engine; compose the one that exists. Must not let the agent write the anchor unreviewed. No new module boundary for a single consumer.
  • Success — SC-1 a finite run produces a doc valid against the ICS shape · SC-2 the steps recompose under a second config · SC-3 warning-free build, green tests, behavior verified.

A minimal implementation ICS

Small work, small anchor — all three parts still appear.

  • Intent — Replace the provisional delay stub with a real cancellation-aware delay so flows pause without a busy-wait.
  • Constraints — Must not change the step contract. Async only — never block a thread. Honor Tier-A teardown: a cancelled delay leaves no pending timer.
  • Success — SC-1 a delayed flow resumes after the interval · SC-2 cancelling cancels the delay with no leaked timer (asserted) · SC-3 the old stub is deleted, not left alongside.

What a bad anchor looks like

SmellConstraints written as “do X, then Y, then Z.”
FixThat's a plan. Rewrite as “must not…” boundaries; move steps down a rung.
SmellTwo pages of detail.
FixPast the U-curve optimum. Cut to durable why + boundaries + a checkable bar.
SmellSuccess reads “works correctly / high quality.”
FixNot observable. Replace with SC-* acceptance checks or parity gates.
SmellThe agent edited the anchor mid-build to “match reality.”
FixDrift leaked in. Revert; route through the amendment gate.
