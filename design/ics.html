01

Why agents need an anchor

An agent with a loose brief doesn't stall. It confidently builds the wrong thing — and everything downstream inherits the mistake.

Give an agent a vague goal and it fills the gaps with guesses, ships something plausible, and moves on. The plan, the tests, and the code all get written against those guesses, so by the time the work looks wrong it's wrong all the way down. The fix isn't more supervision mid-flight — it's pinning down what the work is before it starts, in a form the agent can't quietly wander from.

That pinned-down artifact is the anchor: one page of Intent, Constraints, and Success. Small enough to author in minutes, fixed enough to steer weeks of work.

02

Freeze the top layer

A stream of work has layers. Intent sits on top — the durable why. Below it, a plan; below that, tests; at the bottom, code. Each layer is derived from the one above.

You don't freeze all of them — that's just waterfall. You freeze the top layer and let the agent regenerate the rest against it. Intent is stable; the code beneath it is cheap to redo. So you stay spec-anchored, not spec-as-source: humans own the anchor and read the diffs, the agent owns everything below.

Fig. 1  ·  freeze the top layer; regenerate the rest against it
Why "layer," not "step" The layers aren't a sequence you walk once — they're a stack that stays live. Change the anchor and everything below is regenerated from it. That's the whole point of putting Intent on top and holding it there.
03

Hold it fixed

Two things make an anchor work: authoring it well, and holding it still. The second matters more than it sounds.

Let the anchor change freely and the drift you're shipping leaks back into it — the guesses harden into the spec, and now you're steering by a corrupted map you still trust. A wrong anchor is worse than none: it launders bad direction as authority.

Fig. 2  ·  the same shipped drift, two anchors

Drift flows downhill into the work. It must never flow uphill into the anchor.

The counterintuitive part In one 5,000-run study, a random rule-set scored as well as a curated one on any single task — presence mattered as much as content. But single-task score is the wrong axis. What holding the anchor fixed protects is its integrity across the whole run, not any one output.

When the anchor genuinely must move

Holding it fixed isn't holding it hostage. Sometimes the work proves the anchor wrong — the upstream pivot — and it should change. What's banned is the quiet edit. Soft-lock, not immutability:

  • No auto-mutation. The agent never edits the anchor as a side effect of shipping.
  • Every change is a gated decision. An amendment is proposed, then confirmed by the owner — the agent can propose but never approve its own change.
  • Default is work within the anchor, not amend it. Moving a guardrail is deliberate, and rare.

This isn't a new mechanism — it's the repo's existing protected-paths and required-review rules, applied to the anchor.

Fig. 3  ·  an amendment is a gate, not a keystroke
04

Nest it by scope

One anchor rarely fits a whole system. The same shape stacks at three altitudes — project, feature, implementation — each a real ICS, differing only in reach and how hard it is to move.

Fig. 4  ·  the strata — wider and firmer at the top
  • Constraints inherit and tighten downward. A child may add or tighten a parent's constraints, never loosen them — its allowed space is a subset of the parent's.
  • Success ladders upward. Every child criterion serves a parent one; clearing all the children rolls up to clearing the parent.
  • Gating cost rises with altitude. Amending an implementation ICS is a light approval; amending the project constitution is the heaviest gate, because it invalidates the most work. Drift is cheapest to fix at the leaf, most dangerous at the top.

05

Authoring principles

Each rule traces to a finding or a decision — cited, so the reasoning survives.

P1

Lead with the negatives

In a 5,000-run study, every beneficial rule was a prohibition (“do not X”); every harmful one a directive (“do X”). Constraints are boundaries — procedure belongs in the plan.

→ Guardrails Beat Guidance
P2

One page, on purpose

Specification cost is U-shaped: too little defers it downstream, too much rebuilds waterfall. The optimum is a checkable middle. If it's becoming a PRD, you're on the wrong layer.

→ Eisele · the U-curve
P3

Success is the review bar

Phrase it as observable outcomes with stable IDs (SC-1, SC-2) so reviews, tests, and PRs cite the exact criterion. Never “works well.”

→ NL-fixture boundary conditions
P4

Trace to evidence

Where a constraint has a durable source — an oracle item, an ADR, an observed friction — cite it. A constraint that traces to nothing is just opinion.

→ IntentSpec · ProductSpec
P5

Force the non-functional

Real agent context files carry security and performance only ~15% of the time. The Constraints surface forces exactly the budgets everyone else forgets.

→ Agent READMEs corpus
P6

Scope it in / out / cut

Name what's included, deliberately excluded, and considered-then-dropped. Each line stands alone as a guardrail an agent can act on.

→ ProductSpec
06

Running it

Starting a stream of work is one deliberate act: compose the anchor from the ones above it — project into feature into implementation — and fix it. From then on every activity loops back to that anchor. Planning derives from it, building checks against it, review judges by it — nothing branches off and forgets it.
