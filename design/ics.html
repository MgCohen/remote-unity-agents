01

The drift problem

You set it up — the goal, the guardrails, the plan — and you say go.

And it goes: task, task, task. Then it learns something — a limit it hit, a call it had to make, a better idea — and it writes that down, into the context. Reasonable, once. But it keeps happening, and the context keeps growing. Before every new task the agent reads it back, and by now it's reading a pile: the original plan, plus every insight, tweak, and appended instruction since.

Somewhere in that pile a guardrail got reworded, an instruction picked up a near-duplicate that says something slightly different, the original intent slipped under its own footnotes. Now neither of you can point to the line that's actually true. The plan didn't fail — it drowned.

Fair objection: this only bites if you let the window fill. Clear it — compact, summarise, start each task fresh — and the loop can't corrupt what isn't there.

the usual objection

“I don't let it bloat — I start every task with a brand-new context.”

Except the window is only the part you can see reset. State lives in places a fresh window never touches, and each one can carry a subtly-wrong version of the truth forward:

Anywhere state leaks out and comes back in.

You can wipe the window every task. You can't wipe all of these. Which is the real reason the anchor must be a fixed, protected artifact — not something you re-read from whatever state happens to survive.

The work writes new discoveries into the context and drifts the plan as it goes. A few laps in, the output is validated against the plan — so the drifted plan waves the wrong result through.
02

What an anchor is

The fix is a copy the loop can't reach. Author the durable intent as an anchor — a protected document one layer below the instructions — and validate against that, not the drifting plan.

Same loop, same drift. But the anchor sits underneath it, locked: the work rewrites the instructions all it likes and the anchor never moves. When it's time to check, you check against the anchor — and the drift has nothing to hide behind.

Fig. 4  ·  validate against the anchor, which never drifted
The loop drifts exactly as before — but the anchor sits one layer below it, untouched. Validate against the anchor and the check has firm ground: the result is right, and it saves.

What an anchor actually is

An anchor is small and deliberate — a few lines of context, then a set of rubrics: atomic checks that each answer yes or no.

Rubrics are what make “validate against the anchor” mechanical rather than a judgment call. Constraints lean on what-not-to-do for the same reason: a boundary makes a cleaner yes/no rubric than an open-ended instruction, and it doesn't rot as the work branches.

And that's the whole of ICS: Intent, Constraints, and Success are each an anchor — three small, protected, rubric-shaped docs.

03

Separate files, not one

Intent, Constraints, and Success are separate artifacts — not sections of one document.

Keeping them apart earns three things a single blob can't. Nothing bloats the context — you load only the concern you need. Reads are deterministic: open the Success file and everything in it is success, with nothing to hunt for. And because each file holds one kind of thing, a rubric or eval can check it — that a constraint reads like a constraint, that success is actually measurable.

intent.md
The durable why + North Star.
constraints.md
The laws — mostly what not to do.
success.md
Checkable outcomes, the review bar.
_rollup.md
Auto-generated summary of the tree.

How many files is your call — one page can hold all three when the work is small. Three (plus the optional auto-generated rollup) is the default because it keeps each concern clean and separately checkable.

04

Nesting & compiling

Work happens at a scope — a slice of a feature — and each scope can carry its own anchor.

A slice sits inside a feature, inside a domain, inside the project. Each layer can hold its own Intent, Constraints, and Success — or just the parts it actually pins down. What a layer leaves open, it inherits from the one above.

Fig. 6  ·  a sample layout — the project is always full, each layer adds only what it needs
One sample layout. The project is enforced to carry all three; every layer beneath it adds only the pieces it needs and inherits the rest (dashed) from above — so the deeper you go, the more specific and ephemeral the anchor.

So when a new task starts, its anchor doesn't come from scratch. It's compiled: each dimension is walked down its own column — gathering what every layer defined — and the three columns reconcile into one generated anchor that governs the task.

Fig. 7  ·  a new task compiles its anchor down the stack
A new task walks each dimension straight down its column, gathering what each layer defined; the three columns compile into one generated anchor that governs the task. Both nesting and compiling are optional — a single flat anchor is fine when the work is small.
05

Freeze & the gate

The anchor is fixed: the agent works inside it and doesn't edit it as it goes. That's what breaks the loop in section 01.

But it can't be frozen solid — you started the run because you don't know everything yet, and real discoveries should be able to move it. The agent will reach to fold each new insight straight into the anchor. So the guardrail sits on that reach: it detects the attempt, stops it, and warns you to decide. Nothing changes the anchor silently, and you're not left to catch it later by reviewing thousands of files.

Not only intuition — controlled runs and large corpus studies back the core moves, and mark where to stop.

Eisele · O’Reilly

Read the +13.8pp result honestly. That study scored a single benchmark task, and there random rules matched curated ones — presence drove the gain, not exact wording. So don't over-author an anchor chasing a one-shot score; it won't move.

Point ICS at the axis that's ours: long-running, sequential work, where context drifts across many steps. There the win isn't a higher benchmark — it's that you can trust the anchor still says what you meant, so the whole stream stays aligned with intent. A tightened rule that wouldn't budge a one-shot score is often exactly what keeps a long run on course. Freeze the anchor (§05) so that trust holds.

Every feature or domain carries its own I · C · S set — many rubrics per artifact, not one prose paragraph.

Bad constraint → fix → good

BadConstraints: add the model, wire the endpoint, then update the client.
GoodConstraints: must not change the public API; must not add a new dependency.
BadSuccess: the feature works correctly.
